# Debug 为什么依赖固件

Debug 会直接执行 MIPS 指令、读写内存和外设寄存器。使用 C、内联汇编或手写汇编，都会遇到同样的地址、资源归属和 ABI 问题。

## 三层兼容性

| 层次 | 需要匹配的内容 | 原因 |
|---|---|---|
| CPU / SoC | 指令集、缓存、USB控制器、时钟和中断寄存器 | 不同 JZ 芯片的控制器布局可能不同 |
| 板级硬件 | USB检测GPIO及极性、LCD、可用RAM | 相同芯片的不同机器也可能使用不同接线 |
| 固件内核 | 任务函数、TCB布局、全局堆、tick IRQ、服务表ABI | 原厂升级、编译和链接会移动函数与全局变量 |

当前 Debug 的USB寄存器驱动、RAM访问和LCD复制含直接硬件操作；后台共存还需要原厂调度器分配任务、原厂全局堆保存驻留程序、tick中断唤醒任务，并与原生USB服务交接资源。即使把这些调用全部改写成汇编，也必须知道正确的地址和参数布局。

公开SDK的部分API可从BDA运行时导入表取得函数地址，减少固定地址的数量；未导出的RTOS/USB内部状态仍需要独立核对。RAM模块使用同一后台任务与分配块，因此也继承这些依赖。

## 通用BDA的含义

9588通用BDA包含每个已核对芯片/固件的配置与驻留镜像。启动器比较五张服务表和关键代码CRC，选择唯一匹配的绑定；只装载该芯片的一份驻留程序。界面显示的版本字符串用于说明来源，不用它独自决定是否兼容。

本次原厂输入分别显示JZ4740 V3.30、JZ4730 V1.30、JZ4720 V3.2；它们属于不同内核分支，数字大小不表示能否使用同一个调试文件。

因此兼容性实际取决于内部布局和ABI，而非版本数字本身。两个标号不同的固件如果关键指纹与布局相同，可能共用绑定；同一个版本号下不同芯片的固件，也可能需要不同驱动、地址和GPIO极性。新增固件改变这些内容时，要补充核对与验证。

动态读取服务表、检测控制器或扫描代码模式可以减少绑定工作，但仍须验证函数签名、结构和资源所有权。当前实现只启用已核对的绑定，不把相似的MIPS指令当作所有固件都兼容的依据。

如果完全接管机器，自己实现调度、内存、存储和外设驱动，可以减少对原厂内核的依赖；这需要另一套完整运行环境。当前设计保留原厂菜单和其他BDA运行，采用受指纹保护的后台协作方式。
